# merge-queue-like-bors

A demonstration of running GitHub's merge queue like [bors](https://github.com/rust-lang/bors):
expensive CI runs once, on the tip of the queue batch, not on every PR individually.

## The problem

[Bors](https://github.com/rust-lang/bors) was created to ensure tip-of-tree is always green
(the "PR 1 and PR 2 pass individually but break when merged together" problem), and to batch
CI: running expensive jobs once across a group of PRs rather than once per PR.

GitHub's native merge queue solves the first problem but not the second — it runs the full
test suite on every queue entry independently, which can be very expensive.

## WARNING: Design is Unsafe

**DO NOT USE THIS DESIGN.** Live testing in `bootc-dev/ci-sandbox` under both grouping strategies (ALLGREEN and HEADGREEN) confirms that skipping heavy CI on non-tip merge queue entries is fundamentally incompatible with how GitHub evaluates and merges queue entries. Under-tested code will merge into `main` regardless of which grouping strategy is configured.

This repository is kept for historical/documentation purposes to explain *why* this approach fails, so others do not make the same mistake.

## Why it fails

The design assumes that non-tip entries can safely skip heavy CI and "wait" for the tip to validate the combined state. This assumption is wrong under both grouping strategies, for different but related reasons.

The root cause is an asymmetry in how GitHub's merge queue handles eviction: when an **earlier** entry fails, all **later** entries are rebuilt with new speculative merge SHAs and re-tested. But when a **later** entry (the tip) fails and is evicted, **earlier** entries keep their existing SHAs and their already-reported status check results. GitHub does not re-dispatch `merge_group` events for entries whose SHAs have not changed. Once a status check result (including "skipped," which counts as success) is reported for a commit SHA, GitHub treats it as definitive.

### Under ALLGREEN (empirically confirmed)

Under ALLGREEN ("Only merge non-failing pull requests" enabled), every queue entry must individually pass its required status checks. GitHub does not wait for the entire batch — each entry merges as soon as its own checks pass. When `compute-ci-level` skips heavy jobs for a non-tip entry (PR\_A), those jobs are reported as "skipped" (= success), and the sentinel `required-checks` job passes. GitHub merges PR\_A immediately, *before the tip (PR\_B) has even finished running*.

This was confirmed empirically in `bootc-dev/ci-sandbox` with PRs #76 and #77: PR #76 (non-tip, heavy jobs skipped) merged at 21:54:24Z, while PR #77's (tip) `test-integration` failures completed at 21:54:26–27Z. PR #76 merged 2–3 seconds *before* the tip's heavy checks even finished failing.

This is not a race condition in the traditional sense — it is ALLGREEN working as designed. The design's original assumption ("ALLGREEN holds the batch until all entries pass") was simply wrong about what ALLGREEN means.

### Under HEADGREEN (empirically confirmed)

Under HEADGREEN ("Only merge non-failing pull requests" disabled), only the last/head entry's checks must pass for the batch to merge. GitHub still dispatches `merge_group` events for non-head entries, and those entries still report status check results.

When the head entry (PR\_B) fails, PR\_A merges on the strength of its existing cheap-only "Success" — no new `merge_group` event is dispatched for PR\_A because its speculative merge SHA (`base + PR_A`) was never affected by PR\_B's failure or eviction. The outcome is the same as ALLGREEN: PR\_A lands on `main` without heavy CI, just via a different timing gate.

This was confirmed empirically in `bootc-dev/ci-sandbox` (ruleset switched to HEADGREEN) with PRs #78 and #79: PR #79's (tip) `test-integration` jobs failed at 23:50:09–16Z UTC and its `required-checks-merge` sentinel failed at 23:50:18–21Z; PR #78 (non-tip, heavy jobs skipped, cheap "Success" since 23:50:14Z) merged at 23:50:24Z — three seconds after the tip's own required checks had already failed, and 16 seconds *before* the tip was formally evicted (23:50:40Z).

The one nuance versus ALLGREEN: under HEADGREEN, GitHub did wait for the tip's own check results to resolve before merging the earlier entry (unlike ALLGREEN, where the non-tip entry merged while the tip was still mid-run, without regard to the tip at all). But once the tip's outcome was known — pass *or fail* — GitHub merged the earlier entry using its own stale, cheap-only status rather than either re-testing it as the new head or failing the batch as a unit. So HEADGREEN doesn't provide the "batch only merges if the full-suite result on the tip is known-good" guarantee this design depends on either.

## How it works

### CI tiers

Three tiers of jobs run depending on context:

| Tier | Jobs | When |
|------|------|------|
| 0 | `validate` (cheap checks) | Every PR, every merge queue entry |
| 1 | `build` matrix | `ci/tier-1` labeled PRs; `ci/merge`; forced runs; merge queue tip |
| 2 | `test-integration` matrix | Merge queue tip only (or forced) |

The tip can opt out of tier-2 with the `ci/skip` label (e.g. a docs-only change
that happens to land as queue tip) — it then runs tier-0 only, same as a
non-tip entry. `ci/skip` only affects the merge queue; on a plain PR event it
has no effect. If a PR carries both `ci/merge` (for early feedback) and
`ci/skip`, it gets the full suite on the PR itself but not once it's the
merge-queue tip.

The `compute-ci-level` job queries the GitHub GraphQL API to detect whether the current
merge queue entry is the tip, then sets the `build_os_matrix` and `integration_os_matrix`
outputs that downstream jobs gate on. Jobs with an empty matrix are skipped, and GitHub
counts skipped as passing for required-checks purposes.

### Flow

```
merge_group fires for each queue entry
        │
        ▼
compute-ci-level
  ├─ query mergeQueue(last: 1).headCommit.oid  (GraphQL API)
  ├─ compare to $GITHUB_SHA
  ├─ if match (or API failure): tier-2  (full suite)
  └─ if no match:               tier-0  (cheap checks only)
        │
        ├─ validate                 ← always, ~seconds
        │
        ├─ build (matrix)           ← tier-1+, skipped otherwise
        │
        └─ test-integration (matrix) ← tier-2 only, depends on build
```

With 4 PRs in the queue (intended behavior, **now known to be unsafe**):

```
PR #1  [not tip]: validate ✓  build: skip  integration: skip  → done in ~30s
PR #2  [not tip]: validate ✓  build: skip  integration: skip  → done in ~30s
PR #3  [not tip]: validate ✓  build: skip  integration: skip  → done in ~30s
PR #4  [tip]:     validate ✓  build ✓  integration ✓✓✓...    → done in Xhr
                                                              ↓
                                                   all 4 PRs merge together
```

In practice, under ALLGREEN PRs #1–3 merge immediately (without waiting
for PR #4), and if PR #4 fails they have already landed without heavy CI.

### The sentinel jobs

Two sentinel jobs coordinate required-checks in a way that keeps PRs unblocked while
still enforcing the full suite in the merge queue.

**The problem they solve:** The `ci/merge` label triggers the full tier-2 suite on a PR for
early feedback. With a single sentinel gating all jobs, a flaky heavy job would block the PR
from even entering the merge queue — where those jobs run fresh anyway. Package artifacts
expire, retries are expensive, and the merge queue itself is the right place for the full gate.

**The solution:**

```
required-checks-merge  ← if: merge_group || workflow_dispatch
  needs: [all jobs]       (skipped on pull_request → result = "skipped")
        │
        ▼
required-checks        ← if: always()
  needs: [validate, compute-ci-level, required-checks-merge]
```

- On a **PR**: `required-checks-merge` is skipped (condition false). `required-checks` sees
  `skipped` which counts as success, so only `validate` gates the PR. Heavy jobs from a
  `ci/merge` label run for feedback but don't block merge-queue entry.

- In the **merge queue**: `required-checks-merge` runs with `always()` so it executes even
  when upstream jobs failed, checks every job, and fails if anything broke. `required-checks`
  then picks up that failure.

Configure **only `required-checks`** as the required status check in repository settings.
No separate merge-queue required check configuration is needed.

### Race conditions (The Fatal Flaw)

As detailed in the WARNING section above, the assumptions previously documented here were false:

- **Tip is kicked out of the queue**: When a later entry (the tip) fails and is evicted, earlier entries keep their existing SHAs and status results. GitHub does not rebuild earlier entries or re-dispatch `merge_group` events for them. The earlier entry's cheap-only "Success" is treated as the definitive result.
- **No batch hold under ALLGREEN**: Under ALLGREEN, GitHub does not hold all entries until the entire batch passes. Each entry merges independently as soon as its own required checks pass. A non-tip entry with cheap-only success merges before the tip finishes.

## Adapting this to your project

The files to copy and modify:

- **`.github/scripts/compute-ci-level.mjs`** — edit the `TIER1` and `TIER2` OS matrix
  constants at the top to match your actual build targets. Everything else is generic.
- **`.github/workflows/ci.yml`** — replace the stub `validate`, `build`, and
  `test-integration` jobs with your real CI steps. Keep the `compute-ci-level` job and
  both sentinel jobs unchanged.

The `ci_level` output from `compute-ci-level` is written to the step summary for human
readability but is not used directly by job `if:` conditions. Jobs gate on
`build_os_matrix != '[]'` and `integration_os_matrix != '[]'` instead, since an empty
JSON array is the natural "skip this matrix job" signal in GitHub Actions.

## Sandbox test fixtures

The `ci/` directory contains empty sentinel files used to simulate CI failures without
modifying the workflow. These are specific to this demo repo and would not exist in a real
project.

| File | Effect |
|------|--------|
| `ci/fail-validate` | Makes the `validate` job exit 1 (tier-0 failure, blocks PR) |
| `ci/fail-build` | Makes the `build` job exit 1 (tier-1 failure) |
| `ci/fail-integration` | Makes the `test-integration` job exit 1 (tier-2 failure) |

These were used to verify the sentinel behavior live against `bootc-dev/ci-sandbox`:
- A plain PR (no files) → `required-checks` green immediately
- A PR with `ci/merge` + `ci/fail-build` → `build` fails but `required-checks` still green (PR can be queued); in the merge queue `required-checks-merge` catches the failure and blocks
- A PR with `ci/fail-validate` → `validate` fails, `required-checks` red, PR blocked
